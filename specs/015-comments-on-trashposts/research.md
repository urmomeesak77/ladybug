# Phase 0 Research: Trashpost Comments

All spec Clarifications were resolved in-session (length 1000, verified-e-mail gate,
newest-first batches of 10, cascade on purge). The remaining unknowns are technical
design choices; each is decided below against the existing codebase.

## D1 — Comment public identifier: own 10-char `hash`

**Decision**: Every comment carries its own immutable 10-char `[A-Za-z0-9-_]` `hash`,
generated by `App\Utils\Str::createUniqueHash`, and moderation routes key off that hash.

**Rationale**: Constitution Principle V and the standing rule "no DB auto-increment ids in
user-facing URLs" (memory: *No DB ids exposed*) forbid exposing `comments.id`. Trashposts
already solve this with a `hash`; comments reuse the exact same helper and column shape for
consistency. The hash is enumeration-proof and stable.

**Alternatives considered**: (a) expose the DB id in `/api/admin/comments/{id}` — rejected,
violates Principle V / the no-ids rule. (b) A session-scoped opaque token — rejected,
comments are addressed by admins acting on *other users'* rows, so a per-session digest
doesn't fit; a stable public code does.

## D2 — Hidden state: nullable `hidden_at` timestamp (no boolean)

**Decision**: Moderation "hidden" state is a nullable `hidden_at` timestamp — present =
hidden, null = visible. `Comment::isHidden()` returns `hidden_at !== null`.

**Rationale**: Mirrors the project's established "timestamp presence *is* the state"
pattern (`activated_at`, `deleted_at`, `users.disabled_at`) so there is no separate boolean
to drift out of step. Hide sets `now()`, unhide sets `null` — reversible with no residual
effect (FR-012).

**Alternatives considered**: a `bool is_hidden` — rejected for inconsistency with the rest
of the schema and losing the "when was it hidden" signal for free.

## D3 — Delete is a hard delete (no SoftDeletes on Comment)

**Decision**: Permanent comment deletion is a real row removal (`forceDelete`/`delete` on a
model without the `SoftDeletes` trait). "Hide" is the reversible tool; "delete" is
irreversible (spec Assumptions; FR-013; US4).

**Rationale**: The spec explicitly separates a reversible hide from a permanent delete and
requires the deleted comment to be unrecoverable through the application. A comment has only
two states (visible / hidden) plus removal — unlike a trashpost's activation+soft-delete
lifecycle. Not adding `SoftDeletes` keeps the model honest: there is no tombstone to leak.

**Alternatives considered**: soft-delete comments too — rejected, it would make "permanent"
deletion recoverable and contradict FR-013/SC-006.

## D4 — Purge cascade via DB foreign key `cascadeOnDelete`

**Decision**: `comments.trashpost_id` is a foreign key with `cascadeOnDelete()`. When a
trashpost is **purged** (`ModerationService::purge` → `forceDelete`, a real row delete), the
database cascades and removes its comments (FR-020). Soft-deleting/hiding a trashpost does
**not** remove the row, so nothing cascades and the comments are retained (just unreachable
through public views).

**Rationale**: The cascade is a data-integrity guarantee best enforced at the schema level;
it requires **no change to `ModerationService::purge`**, which already issues a hard delete.
Laravel's SQLite test connection enables `foreign_key_constraints` by default, so the
cascade is exercised in `:memory:` feature tests too. Soft delete (`deleted_at`) never
triggers the FK cascade because the row still exists — exactly the required asymmetry.

**Alternatives considered**: delete comments explicitly inside `purge()` — rejected as
redundant with the FK and it couples the moderation service to comments; the FK is
declarative and self-documenting. (A feature test still asserts the end-to-end cascade.)

## D5 — Orphaned author: nullable `user_id` + `username` snapshot

**Decision**: `comments.user_id` is nullable with `nullOnDelete()`; a `username` column
snapshots the author's name at creation time. Display name = `user?->name ?? username`
(via `CommentResource`), mirroring `TrashpostResource::authorName()`.

**Rationale**: When an author account is later hard-deleted (013 allows it), the FK nulls
`user_id` rather than cascading the comment away, so the comment is retained (edge case
"Author account later removed"). The `username` snapshot means the retained comment still
shows who wrote it instead of a bare "unknown", matching how orphaned trashposts already
behave. This is a graceful fallback, not a crash.

**Alternatives considered**: cascade-delete comments when the author is removed — rejected,
the spec says the comment is retained with a graceful author fallback, not destroyed.

## D6 — Listing pagination: keyset cursor, newest-first, batch 10

**Decision**: `GET /api/posts/{hash}/comments` returns the newest 10 comments plus a
`meta.next_cursor` (opaque) and `meta.total` (public count). "Load more older comments"
re-requests with `?before=<cursor>`; ordering is `created_at DESC, id DESC`. Batch position
is not reflected in the page URL (FR-019, clarified).

**Rationale**: Mirrors the feed's keyset approach (`GET /api/posts?start=…`), which is
robust when new rows are inserted at the head — a freshly posted comment prepended to the
top never shifts an older page or causes a skipped/duplicated row (offset paging would).
The cursor encodes the last row's `(created_at, id)`; it is opaque to the client.

**Alternatives considered**: page-number offset paging — rejected, prepends shift offsets
and duplicate/skip comments across "load more" clicks. This matches the site convention
(the feed already uses keyset).

## D7 — Public count vs. admin visibility

**Decision**: `meta.total` in the list response is always the **public** count — visible
(non-hidden) comments only (FR-015) — even for an admin viewer. The list *rows* returned to
an admin additionally include hidden comments, each flagged `hidden: true`; rows returned
to guests/members exclude hidden comments entirely at the query layer.

**Rationale**: FR-015 says the *publicly shown* count excludes hidden/deleted; the count is
a public signal, so it stays public regardless of who is looking. Admin visibility of hidden
rows (FR-011) is a separate concern handled by the row query, viewer-aware exactly like
`TrashpostsApiController::show` resolves hidden posts for admins/owners.

## D8 — Create gate: `auth:sanctum` + `verified` + throttle at the route

**Decision**: `POST /api/posts/{hash}/comments` mounts behind
`['auth:sanctum', 'verified', 'throttle:comments']`, identical in spirit to the upload route
(`POST /api/posts`). `CreateCommentRequest` validates the body server-side.

**Rationale**: FR-004 requires the gate at the data layer, not just the UI. `verified` is
the same `EnsureEmailIsVerified` alias 008 already uses, so an unverified signed-in user
gets a `403` and a guest gets `401` — no comment created — independent of the SPA. A
dedicated `comments` limiter (env-tunable, keyed by user) throttles comment spam without
sharing the heavier upload budget; it is app config, not a dependency.

**Alternatives considered**: gate only in the controller — rejected, middleware is the
established, testable boundary. Reuse `throttle:uploads` — rejected, uploads and comments
have different cost profiles and abuse patterns; a separate cap is clearer.

## D9 — Moderation controls reuse the shared `ActionMenu` + `useNotice`

**Decision**: Per-comment admin controls render through the existing `ActionMenu` kebab
(013) and confirm permanent delete through `useNotice().ask` — the same components
`AdminPostActions` uses. Items are state-driven: a visible comment offers Hide + Delete; a
hidden comment offers Unhide + Delete (Delete always confirmed).

**Rationale**: 013 already established one shared, accessible, keyboard-operable menu for all
admin per-row actions; reusing it satisfies Principle IV a11y for free and keeps the UI
consistent. `useNotice` already provides the confirm dialog used for trashpost
purge/soft-delete. No new UI primitives.

**Alternatives considered**: bespoke inline buttons per comment — rejected, duplicates
solved a11y/keyboard behavior and diverges from the established moderation UX.

## D10 — Output safety: React auto-escaping, plain text only

**Decision**: Comment body is stored verbatim and rendered as a plain-text React child
(`{comment.body}`), never via `dangerouslySetInnerHTML`. Newlines may be presented with CSS
`white-space: pre-wrap`; no markup is interpreted.

**Rationale**: React escapes string children by default, so any `<`, `>`, `&`, or script
characters display literally and never execute (FR-009, SC-007). Keeping the body plain text
(no rich formatting — spec Assumptions) means there is no sanitizer to write or dependency to
add. `pre-wrap` preserves the author's line breaks without enabling HTML.

**Alternatives considered**: a markdown/rich-text renderer — rejected, out of scope (plain
text v1) and would add a dependency and an XSS surface.
